# ЛР5: как устроено приложение погоды

Этот разбор объясняет существующий код простыми шагами: какие данные получаем, зачем нужны разные классы,
где выполняется запрос и как результат становится карточкой на экране.
Примеры температуры ниже условные — это не актуальная сводка погоды.

## С чего начать

Сначала прочитай разделы про три модели и два запроса. Затем перейди к репозиторию и экрану.
Подробности сохранения избранного можно читать после того, как станет понятен обычный поиск города.

Главные три вещи:

1. `City` — данные города: название, страна и координаты.
2. `Weather` — текущая погода этого города и список прогноза.
3. `ForecastDay` — данные одного дня из списка прогноза.

Это обычные Dart-классы, как `CalendarEvent` в ЛР4. Они сами ничего не скачивают и не рисуют.

## Сначала ответ на вопрос про кэш

**Сейчас погодного кэша у нас нет.** Мы не сохраняем большой ответ сервера на устройство, чтобы потом искать в нём погоду.

После запроса нужные значения из JSON превращаются в объекты `City`, `Weather`, `ForecastDay`.
Полученный `Weather` находится в памяти приложения, и экран читает его поля.
При обновлении погоды отправляется новый запрос. После полного перезапуска объект погоды не восстанавливается автоматически.

На устройство сохраняются только избранные города: их названия, ID, страны, регионы и координаты.
По сохранённым координатам потом можно снова запросить погоду.

| Данные | Где находятся | Восстанавливаются после перезапуска |
| --- | --- | --- |
| Найденные города | Поле `cities` в состоянии экрана | Нет |
| Текущая погода и прогноз | Поле `weather` в состоянии экрана | Нет |
| Избранные города | Список в `FavoritesRepository` и локальное хранилище | Да |

Кэш погоды означал бы, например, сохранение температуры и прогноза вместе со временем получения,
чтобы показать их позднее без нового запроса. Такой возможности мы не делали.

## Зачем три модели, а не одна

Можно написать приложение и с одним большим классом. Но тогда в нём смешаются сведения о городе,
текущие показатели и данные нескольких будущих дней. ТЗ не требует именно эти три модели — это наше разделение данных.

Город существует сам по себе, даже когда его погоду ещё не загрузили.
Поэтому для результата поиска и избранного достаточно `City`: температура там не нужна.
А в прогнозе несколько дней с одинаковым набором полей — удобно представить каждый из них как `ForecastDay`.

### `lib/models/city.dart` — один город

Аналогия с ЛР4: `CalendarEvent` описывал одно событие, а `City` описывает один город.
Слово «модель» здесь означает просто класс для связанных данных.

| Поле | Что означает |
| --- | --- |
| `id` | Уникальный номер города, который прислал сервис |
| `name` | Название, например «Ханты-Мансийск» |
| `country` | Страна |
| `region` | Регион |
| `latitude` | Широта — часть координат |
| `longitude` | Долгота — вторая часть координат |

Пример создания такого объекта:

```dart
final city = City(
  id: 1503772,
  name: 'Ханты-Мансийск',
  country: 'Россия',
  latitude: 61.00187,
  longitude: 69.02728,
);
```

Теперь `city.name` — название, а `city.latitude` — широта.
В этом объекте нет ни температуры, ни прогноза.

Зачем координаты? Сервис погоды принимает координаты места.
Сначала мы находим город по названию, а затем запрашиваем погоду по его широте и долготе.

`fullName` собирает название вместе с регионом и страной. Это помогает выбрать нужный город среди одноимённых.
Запись `String get fullName` — getter: обращение выглядит как к полю `city.fullName`, но внутри выполняется функция.

`City.fromJson(...)` создаёт город из данных сервера или сохранённого избранного.
`city.toJson()` превращает город в карту значений для сохранения.

### `lib/models/forecast_day.dart` — прогноз одного дня

```dart
class ForecastDay {
  final DateTime date;
  final double minimum;
  final double maximum;
  final int code;

  ForecastDay({
    required this.date,
    required this.minimum,
    required this.maximum,
    required this.code,
  });
}
```

Здесь всего четыре поля:

- `date` — дата этого дня;
- `minimum` — минимальная температура за сутки;
- `maximum` — максимальная температура за сутки;
- `code` — числовое обозначение погодных условий.

Например:

```dart
final day = ForecastDay(
  date: DateTime(2026, 10, 21),
  minimum: -2,
  maximum: 4,
  code: 3,
);
```

Это означает: 21 октября минимум −2 °C, максимум +4 °C, код 3 — пасмурно.
**Это данные дня, а не карточка Flutter.** Виджет карточки создаётся позже в `buildForecastDay`.

Пять объектов `ForecastDay` позволяют описать пять дней. Отдельных запросов для каждого дня не нужно:
все дни приходят в одном ответе погоды.

### `lib/models/weather.dart` — весь результат погоды выбранного города

У `Weather` есть текущие показатели:

| Поле | Что хранит |
| --- | --- |
| `city` | Объект города `City` |
| `temperature` | Текущую температуру |
| `humidity` | Влажность |
| `wind` | Скорость ветра |
| `pressure` | Давление или `null`, если его нет |
| `code` | Код текущих погодных условий |
| `isDay` | День сейчас или ночь по ответу сервиса |
| `time` | Время, к которому относятся текущие данные |
| `forecast` | Список объектов `ForecastDay` |

Два особенно важных поля:

```dart
final City city;
final List<ForecastDay> forecast;
```

Первое хранит ссылку на объект города. Второе — список объектов дней.
Так же, как в ЛР4 список событий содержал объекты `CalendarEvent`.

Структура одного результата в памяти:

```text
Weather
├─ city → City: Ханты-Мансийск, координаты
├─ temperature: 1.0
├─ humidity: 86
├─ wind: 5.8
├─ остальные текущие показатели
└─ forecast → список
   ├─ ForecastDay: 20 октября, минимум −1, максимум +3
   ├─ ForecastDay: 21 октября, минимум −2, максимум +4
   ├─ ForecastDay: 22 октября, минимум −3, максимум +5
   ├─ ForecastDay: 23 октября, свои показатели
   └─ ForecastDay: 24 октября, свои показатели
```

Когда в коде написано `value.city.name`, это значит: взять объект погоды `value`,
у него взять город `city`, а у города — название `name`.

Когда написано `value.forecast[0].minimum`, берём первый день списка и его минимальную температуру.
Индексы списка начинаются с нуля, поэтому `[0]` — первый элемент.

## Почему обычно выполняются два запроса

### Первый запрос — найти город

Пользователь вводит «Ханты-Мансийск». Сервис поиска возвращает подходящие места и их координаты.
Вот сокращённый пример JSON-ответа:

```json
{
  "results": [
    {
      "id": 1503772,
      "name": "Ханты-Мансийск",
      "country": "Россия",
      "latitude": 61.00187,
      "longitude": 69.02728
    }
  ]
}
```

JSON — текстовый формат передачи данных. Фигурные скобки объединяют именованные значения,
квадратные скобки обозначают список. `results` — список результатов поиска.

Из каждого элемента `results` создаётся `City`.
Если результат один, приложение сразу загружает его погоду. Если несколько — пользователь выбирает нужный.

### Второй запрос — погода по координатам

Передаём широту и долготу выбранного города. В ответе получаем текущие показатели и прогноз.
Для наглядности ниже оставлены три дня; наш запрос обычно возвращает пять.

```json
{
  "current": {
    "temperature_2m": 1.0,
    "relative_humidity_2m": 86,
    "wind_speed_10m": 5.8,
    "surface_pressure": 1001.6,
    "weather_code": 73,
    "is_day": 1,
    "time": "2026-10-20T12:00"
  },
  "daily": {
    "time": ["2026-10-20", "2026-10-21", "2026-10-22"],
    "temperature_2m_min": [-1, -2, -3],
    "temperature_2m_max": [3, 4, 5],
    "weather_code": [73, 3, 0]
  }
}
```

`current` — текущие показатели. `daily` — данные дней прогноза.
Мы запрашиваем нужные показатели параметрами запроса, а не скачиваем погоду всех городов.

## Как JSON превращается в наши объекты

### `lib/data/weather_api_client.dart` — отправить запрос и прочитать ответ

У этого класса три основные функции:

- `searchCities(name)` собирает адрес поиска города;
- `getWeather(latitude, longitude)` собирает адрес запроса погоды;
- `getJson(address)` выполняет запрос, проверяет ответ и разбирает JSON.

Сам запрос:

```dart
final response = await client
    .get(address)
    .timeout(const Duration(seconds: 15));
```

`get` отправляет запрос на получение данных. `await` ждёт результат, не останавливая работу всего интерфейса.
`timeout` ограничивает ожидание пятнадцатью секундами.
`response` — объект ответа: в нём есть статус и содержимое.

После проверки статуса выполняется:

```dart
final data = jsonDecode(utf8.decode(response.bodyBytes));
```

Здесь два действия:

1. `utf8.decode` превращает байты ответа в строку, правильно читая русский текст.
2. `jsonDecode` превращает JSON-строку в карты `Map` и списки `List`.

**На этом шаге объект `Weather` ещё не создан.** Получилась карта с ключами `current`, `daily` и их значениями.

Пример чтения карты:

```dart
data['current']['temperature_2m']
```

Читается так: из `data` взять раздел `current`, а из него — `temperature_2m`.
API-клиент возвращает разобранные данные репозиторию.

### `lib/repositories/weather_repository.dart` — собрать модели

Репозиторий нужен, чтобы экран работал с понятными полями `weather.temperature`,
а не разбирал названия ключей JSON при построении каждой карточки.

В `searchCities` цикл создаёт объекты городов:

```dart
for (final item in results) {
  cities.add(City.fromJson(item as Map<String, dynamic>));
}
```

`item` — очередной элемент списка от сервера. `City.fromJson` создаёт из него объект,
а `cities.add` добавляет объект в наш список городов.

В `getWeather` сначала разделяем ответ:

```dart
final current = data['current'] as Map<String, dynamic>;
final daily = data['daily'] as Map<String, dynamic>;
final dates = daily['time'] as List<dynamic>;
```

Это обычные переменные для удобного обращения к частям ответа, не отдельные запросы и не файлы кэша.

### Как собирается список дней

В `daily` данные расположены параллельными списками. Значения с одинаковым индексом относятся к одному дню:

| Индекс | Дата | Минимум | Максимум | Код |
| --- | --- | --- | --- | --- |
| 0 | 20 октября | −1 | +3 | 73 |
| 1 | 21 октября | −2 | +4 | 3 |
| 2 | 22 октября | −3 | +5 | 0 |

Вот реальный цикл из репозитория:

```dart
final List<ForecastDay> forecast = [];

for (int index = 0; index < dates.length; index++) {
  forecast.add(
    ForecastDay(
      date: DateTime.parse(dates[index] as String),
      minimum: (daily['temperature_2m_min'][index] as num).toDouble(),
      maximum: (daily['temperature_2m_max'][index] as num).toDouble(),
      code: daily['weather_code'][index] as int,
    ),
  );
}
```

Когда `index == 0`, берутся дата, минимум, максимум и код первого дня. Создаётся один `ForecastDay` и добавляется в `forecast`.
Потом `index` становится 1 — создаётся второй день. Так продолжается до конца списка дат.

Никаких виджетов в этом цикле нет: **мы пока собираем данные**.
`DateTime.parse` переводит строку даты в объект `DateTime`.
`as num` означает, что ожидаем число, а `.toDouble()` приводит его к дробному типу.

После цикла создаётся `Weather`: текущие поля берутся из `current`,
а в поле `forecast` передаётся только что собранный список.
В поле `city` передаётся уже выбранный объект города — повторно искать город не требуется.

Функция возвращает один `Weather`, внутри которого находятся и текущая погода, и все дни прогноза.

## Как результат попадает на экран

### `lib/main.dart` — запуск

`main()` вызывает `runApp`. `WeatherApp` создаёт `MaterialApp`, задаёт тёмную тему и открывает `WeatherScreen`.
Как в ЛР4: главный виджет приложения — `StatelessWidget`, а экран с меняющимися данными — `StatefulWidget`.

### `lib/pages/weather_screen.dart` — нажатия и меняющиеся данные

`WeatherScreen` создаёт `WeatherState`. Это обычный `State`, как `CalendarState` в календаре.
В нём находятся данные, по которым строится интерфейс.

Начни с этих полей:

| Поле | Смысл |
| --- | --- |
| `cityController` | Позволяет прочитать текст из поля города |
| `cities` | Список найденных городов, пока выбираем нужный |
| `selectedCity` | Выбранный город |
| `weather` | Полученная погода с прогнозом либо `null` |
| `isLoading` | Запрос ещё выполняется |
| `error` | Текст сетевой ошибки либо `null` |

Остальные поля уточняют поведение:

- `hasSearched` отличает начальную подсказку от сообщения «Город не найден»;
- `lastQuery` запоминает отправленное название, чтобы повторить именно его;
- `inputError` показывает ошибку пустого ввода;
- `favorites` — объект для работы с избранными городами;
- `favoritesReady`, `savingFavorite`, `favoritesError` относятся только к загрузке и сохранению избранного;
- `scrollController` позволяет вернуть прокрутку к началу при выборе города;
- `repository` — объект, через который экран получает города и погоду.

### Что происходит при нажатии поиска

Кнопка получает обработчик:

```dart
onPressed: isLoading ? null : searchCities,
```

Если идёт загрузка, кнопка выключена: обработчик равен `null`.
Иначе нажатие вызывает функцию `searchCities` состояния экрана.

Она читает текст, убирает пробелы по краям через `trim`, проверяет пустоту,
включает загрузку и вызывает:

```dart
final results = await repository.searchCities(query);
```

Если найден один город, вызывается `loadWeather(results.first)`.
Если несколько, `cities` показывается списком карточек. Нажатие на карточку вызывает `loadWeather(city)`.

### Самый важный участок `loadWeather`

```dart
final result = await repository.getWeather(city);
if (!mounted) {
  return;
}
setState(() {
  weather = result;
  isLoading = false;
});
```

Разбираем по строкам:

1. Просим репозиторий получить погоду выбранного города и ждём объект `Weather`.
2. Проверяем, существует ли ещё экран: его могли закрыть во время ожидания.
3. Записываем объект в поле `weather`.
4. Выключаем признак загрузки.
5. Благодаря `setState` Flutter снова вызывает `build` и показывает новое состояние.

`result` — временное имя результата внутри функции. `weather` — поле состояния,
из которого интерфейс будет читать данные после завершения функции.

### Как данные становятся карточками

В `build` берётся текущий результат:

```dart
final current = weather;
```

Если он есть, добавляется блок погоды:

```dart
if (current != null) buildWeatherDetails(current),
```

`buildWeatherDetails` вызывает `buildCurrentWeather(value)` для главной карточки,
а затем проходит по дням:

```dart
for (final day in value.forecast) buildForecastDay(day),
```

**Вот здесь уже создаются виджеты.** `day` — данные одного дня,
а `buildForecastDay(day)` возвращает карточку `Card` с текстом и значком.
Внутри неё читаются `day.date`, `day.minimum`, `day.maximum`, `day.code`.

Это похожий принцип на ЛР4: там для каждого `CalendarEvent` строилась карточка события,
здесь для каждого `ForecastDay` — карточка прогноза.

Не путай три названия:

| Название | Что это |
| --- | --- |
| `ForecastDay` | Класс данных одного дня |
| `forecast` | Список объектов этих дней |
| `buildForecastDay` | Наша функция, которая создаёт виджет карточки из данных дня |

`return Card(...)` не запускает нажатие. Он возвращает описание элемента интерфейса.
Обработчики `onPressed` и `onTap` выполняются позже, когда пользователь нажимает кнопку или карточку.

### Какие состояния показываются

| Состояние | По каким данным понимаем | Что видно |
| --- | --- | --- |
| До поиска | Поиск ещё не запускали | Подсказка ввести город |
| Загрузка | `isLoading == true` | Индикатор ожидания |
| Успех | В `weather` есть объект | Текущая погода и прогноз |
| Несколько городов | В `cities` есть результаты | Список для выбора |
| Пустой результат | Поиск завершён, ошибки нет, городов нет | «Город не найден» |
| Ошибка | В `error` есть сообщение | Сообщение и «Повторить» |

Запросы выполняются в обработчиках, а не в `build`.
Поэтому повторная отрисовка экрана сама по себе не скачивает погоду заново.
В ЛР5 один экран: `Navigator`, который открывал форму в ЛР4, здесь не используется.

## Откуда берутся снежинка и описание

### `lib/weather_display.dart`

Сервис присылает `weather_code`, например 73. В нашей карте `weatherDescriptions` этому числу соответствует «Снег».
В главной карточке вызывается:

```dart
Text(weatherDescription(value.code))
```

А функция `weatherIcon` выбирает значок через обычные `if`. Для снега она возвращает `Icons.ac_unit`.
Экран создаёт виджет `Icon` с этим значком. Значки готовые, встроенные во Flutter; свои картинки мы не рисовали.

`formatTemperature` округляет число и добавляет плюс для положительной температуры.
`formatDate` собирает день недели и дату для подписи прогноза.
Эти функции не запрашивают и не сохраняют данные — только подготавливают их для показа.

## Где находятся избранные города

### `lib/repositories/favorites_repository.dart`

Это отдельная задача: сохранить список выбранных мест, чтобы не вводить их каждый раз.
Основные поля:

| Поле | Что хранит |
| --- | --- |
| `cities` | Список избранных объектов `City` в памяти |
| `preferences` | Объект готового пакета для чтения и записи на устройство |
| `storageKey` | Название записи `weather_favorites` |

Три основные функции:

- `load()` читает сохранённый список при запуске;
- `contains(city)` проверяет, добавлен ли город, сравнивая его ID;
- `toggle(city)` добавляет отсутствующий город либо удаляет уже добавленный.

`shared_preferences` — подключённый готовый пакет, мы его не писали.
Как в ЛР4, он сохраняет строку JSON, а в браузере использует LocalStorage.

```text
Список City → toJson → jsonEncode → shared_preferences → LocalStorage
```

При загрузке:

```text
LocalStorage → строка → jsonDecode → City.fromJson → список City
```

В `toggle` сначала создаётся копия списка. Новая версия записывается в хранилище,
и только после успешной записи заменяет видимый список.
Поэтому при ошибке сохранения звезда не показывает ложное успешное добавление.

Почему здесь достаточно `City`? Для повторного открытия нужны название и координаты,
а старая температура уже могла измениться. Погоду при выборе избранного мы получаем новым запросом.

| Действие | Какие запросы выполняются |
| --- | --- |
| Новый поиск города | Сначала поиск, затем погода выбранного города |
| Обновление погоды верхней кнопкой | Только погода по уже известным координатам |
| Выбор избранного города | Только погода по сохранённым координатам |
| Нажатие звезды | Запись избранного на устройство, без запроса погоды |

Используй тот же браузер и адрес `http://127.0.0.1:8755`.
Другой порт или `localhost` вместо `127.0.0.1` — другой адрес хранения.
При ошибке чтения избранного его изменение блокируется до успешного повтора, но поиск погоды остаётся доступным.

## Как обработаны ошибки сети

API-клиент проверяет `response.statusCode` до разбора JSON.
Если ответ неуспешный, сервер может прислать обычный текст вместо ожидаемых погодных данных.

| Ситуация | Что делаем |
| --- | --- |
| HTTP 200 | Разбираем ответ |
| HTTP 404 | Показываем, что адрес ресурса сервиса не найден |
| HTTP 500 и другие 5xx | Показываем ошибку сервиса |
| HTTP 429 | Предлагаем подождать и повторить |
| Нет соединения | Показываем сообщение с предложением проверить интернет |
| Ответ не пришёл за 15 секунд | Показываем ошибку ожидания |
| JSON или обязательные поля некорректны | Показываем ошибку разбора данных |

**Неизвестный город — не то же самое, что HTTP 404.** Сервис поиска обычно успешно отвечает,
но не возвращает подходящих городов. Тогда показываем пустой результат.

`WeatherException` — наш простой класс с полем `message`, то есть текстом ошибки.
`throw` передаёт ошибку выше, а `catch` её обрабатывает. Экран записывает сообщение в `error` через `setState`.

Функция `retry()` повторяет погоду для `selectedCity`.
Если ошибка была ещё при поиске, она повторяет сохранённый `lastQuery`.

## Несколько записей Dart из нашего кода

Это справочник: к нему можно возвращаться, когда встретилась непонятная строка.

| Запись | Как читать |
| --- | --- |
| `List<ForecastDay>` | Список, элементы которого — объекты `ForecastDay` |
| `Map<String, dynamic>` | Карта со строковыми ключами и значениями разных типов |
| `Future<Weather>` | Позже функция вернёт объект `Weather` |
| `Future<void>` | Асинхронная функция без возвращаемых полезных данных |
| `async` / `await` | Функция может ждать результат операции |
| `Weather?` | Объект погоды или отсутствие значения `null` |
| `??` | Подставить значение справа, если слева `null` |
| `as int` | Ожидаем, что значение имеет тип целого числа |
| `required` | Этот аргумент конструктора нужно передать |
| `final` | Этой переменной или полю нельзя присвоить другое значение |

`final` у списка не запрещает добавлять его элементы. Он запрещает заменить сам список другим списком.

`factory City.fromJson` — именованный конструктор, который создаёт `City` из карты.
Слово `factory` здесь не означает отдельный сервер или какую-то библиотеку.

Конструктор API-клиента:

```dart
WeatherApiClient({http.Client? client}) : client = client ?? http.Client();
```

Если передали готовый клиент, используем его. Если не передали, создаём обычный `http.Client()`.
Это позволяет тестам подменять сеть. Такой же принцип используется в конструкторе репозитория.

`late final repository` заполняется один раз в `initState`, когда уже доступен `widget.repository`.
Обычный запуск создаёт настоящий репозиторий; тесты могут передать свой.

`mounted` означает, что объект состояния ещё находится в дереве виджетов.
После ожидания сети экран мог быть закрыт, поэтому перед `setState` мы проверяем `mounted`.

`!` после значения означает, что ожидаем его не равным `null`.
Например, давление сначала проверяется условием, а затем читается через `value.pressure!`.
Без предварительной проверки такой знак может привести к ошибке.

## Что из этого уже знакомо по ЛР4

| В календаре | В погоде |
| --- | --- |
| `CalendarEvent` описывает событие | `City`, `Weather`, `ForecastDay` описывают данные погоды |
| `CalendarState` хранит выбранную дату | `WeatherState` хранит выбранный город и результат |
| Репозиторий работает с событиями | Репозиторий получает и собирает погоду |
| Цикл создаёт карточки событий | Цикл создаёт карточки дней прогноза |
| `setState` обновляет календарь | `setState` обновляет состояние поиска и погоды |
| `shared_preferences` сохраняет события | Тот же пакет сохраняет избранные города |

Важное различие: `WeatherRepository` не хранит общий архив погоды, как `EventRepository` хранит список событий.
Он получает данные и возвращает `Weather`. Последний результат хранится в поле `weather` состояния экрана.
Слово «репозиторий» означает место работы с данными, а не обязательно базу данных или кэш.

## Четыре контрольных вопроса из ТЗ

**Какие состояния должен иметь сетевой экран?** Загрузка, успех и ошибка. Для поиска ещё нужен пустой результат.
У нас они определяются полями `isLoading`, `weather`, `error`, `cities`, `hasSearched`.

**Где размещать API client?** В отдельном слое данных. У нас это `lib/data/weather_api_client.dart`.
Там адреса, параметры, отправка запросов, HTTP-коды и ошибки соединения.

**Как обработать HTTP 404 и 500?** Проверить статус до разбора успешных данных.
404 — ресурс сервиса не найден, 500 — ошибка сервера. Показать понятный текст и кнопку повтора.

**Зачем нужен repository?** Чтобы экран получал готовые объекты городов и погоды,
а разбор ответа сервера находился в одном месте, отдельно от виджетов.

## Ещё вопросы для защиты

1. **Зачем несколько моделей?** Город, текущая погода и один день прогноза имеют разные поля и используются по-разному.
2. **Можно ли одним классом?** Можно, но тогда придётся смешать эти данные. Три модели — наш способ их разделить.
3. **Каждая модель делает запрос?** Нет, модели только хранят данные. Запрос выполняет `WeatherApiClient`.
4. **На пять дней нужно пять запросов?** Нет, прогноз всех дней приходит в одном погодном ответе.
5. **Почему сначала ищем город?** Чтобы узнать координаты, которые нужны погодному сервису.
6. **Где лежит последний результат?** В поле `weather` объекта `WeatherState`.
7. **Есть ли кэш погоды?** Нет. Локально сохраняются только избранные города.
8. **Что будет без интернета?** Избранные города можно загрузить из хранилища, но новую погоду получить не получится.
9. **Модель рисует карточку?** Нет. `ForecastDay` хранит данные, `buildForecastDay` создаёт виджет.
10. **Что делает `setState`?** Сообщает Flutter, что данные изменились и интерфейс нужно перестроить.
11. **Делает ли `build` запрос?** Нет. Запросы запускаются обработчиками действий.
12. **Что если найдено два одинаковых названия?** Показываем регион и страну, пользователь выбирает нужный город.
13. **Для чего ID?** Отличает города с одинаковыми названиями при работе с избранным.
14. **Откуда значок снега?** Из встроенного набора Flutter, выбирается по коду погоды.
15. **Нужен ли ключ API?** Для выбранного учебного некоммерческого доступа к Open-Meteo ключ не требуется.
16. **Откуда взялся `http`?** Это готовый подключённый пакет для запросов, показанный в документации Flutter из ТЗ.
17. **Мы написали `shared_preferences`?** Нет, подключили готовый пакет, как в ЛР3 и ЛР4.
18. **Почему может отсутствовать давление?** Поле допускает `null`; тогда показатель просто не рисуется.
19. **Какие единицы используются?** Температура — °C, ветер — м/с, давление — гПа.
20. **Используем ли Navigator?** В текущем приложении погоды нет, всё происходит на одном экране.

`timezone=auto` запрашивает время по координатам города. Мы показываем пришедшие компоненты даты и времени,
не переводя их дополнительно в пояс устройства. `DateTime` строки без смещения не хранит название пояса города.

| Просьба преподавателя | Где изменить |
