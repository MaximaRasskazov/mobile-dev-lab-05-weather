# ЛР5: как работает приложение погоды

## Короткий рассказ

«Приложение ищет город через Open-Meteo. Получает его координаты и по ним делает второй запрос —
текущую погоду и прогноз на пять дней. JSON превращается в обычные Dart-классы.
Экран показывает загрузку, результат, ошибку либо сообщение, что город не найден.
При ошибке запрос можно повторить. Дополнительное задание — избранные города, которые сохраняются локально».

Ниже — пояснения фактического кода. Перед защитой полезно самостоятельно выполнить несколько правок из последней таблицы.

## Разделение файлов

Архитектура из ТЗ: `WeatherScreen → WeatherState → WeatherRepository → WeatherApiClient`.
Это обычные классы; отдельной библиотеки управления состоянием нет.

| Файл | За что отвечает |
| --- | --- |
| `main.dart` | `runApp`, `MaterialApp`, тёмная тема и открытие экрана |
| `models/city.dart` | Данные города, полное название и преобразование JSON |
| `models/weather.dart` | Данные текущей погоды и список дней прогноза |
| `models/forecast_day.dart` | Дата, минимальная и максимальная температура, код погоды одного дня |
| `data/weather_api_client.dart` | Адреса API, параметры, HTTP-запросы и сетевые ошибки |
| `repositories/weather_repository.dart` | Преобразование JSON в модели |
| `repositories/favorites_repository.dart` | Чтение и сохранение списка избранных городов |
| `weather_display.dart` | Русские описания, значки, оформление температуры и даты |
| `pages/weather_screen.dart` | Состояние приложения, обработчики кнопок и виджеты |

В `main.dart` и `WeatherScreen` можно передать готовый репозиторий. В обычном запуске аргумент не передаётся,
поэтому создаётся настоящий репозиторий. В тестах передаётся вариант с подменённым HTTP-клиентом.
Это позволяет проверять ошибки сервера без изменения рабочего приложения и без дополнительных библиотек тестирования.
Запись конструктора `: client = client ?? http.Client()` означает: взять переданный клиент,
а если его нет — создать настоящий. Двоеточие здесь инициализирует поле перед выполнением тела конструктора.

## Какие данные хранят модели

`City`: уникальный `id` из сервиса, `name`, `country`, `region`, `latitude`, `longitude`.
Одинаковые названия не означают одинаковые города. Для избранного сравниваются ID, для погоды передаются координаты.
`fullName` — getter: обращение выглядит как к полю, но значение собирает функция из названия, региона и страны.

`City.fromJson` создаёт объект из карты `Map<String, dynamic>`.
У карты строковые ключи, например `name`, а значения разных типов.
`as String` указывает ожидаемый тип. Координата может прийти целым или дробным числом,
поэтому используется `(data['latitude'] as num).toDouble()`.
`?? ''` подставляет пустую строку, если страна или регион отсутствуют.
`toJson()` выполняет обратное преобразование для сохранения избранного.

`Weather`: город, температура, влажность, ветер, необязательное давление, код погоды,
признак дня, время данных и `List<ForecastDay>`.
`double? pressure` разрешает отсутствие давления: при `null` показатель не рисуется.

`ForecastDay`: дата и прогноз на одни сутки. Значения `minimum` и `maximum` — минимум и максимум за сутки,
а не отдельные точные температуры в конкретный час.
Поля моделей `final`: после создания объекта им нельзя присвоить другое значение.

## Как проходит запрос

1. Пользователь вводит город. `searchCities` читает `cityController.text.trim()`.
2. Если строка пустая, выставляется `inputError` и запрос не отправляется.
3. Состояние меняется на загрузку через `setState`: старый результат очищается, включается индикатор.
4. Репозиторий вызывает API-клиент. Клиент собирает `Uri.https`, выполняет `client.get` и проверяет ответ.
5. `jsonDecode` превращает строку JSON в карты и списки. Репозиторий создаёт `City`.
6. Если найден один город, сразу вызывается `loadWeather`. Если несколько — показывается список для выбора.
7. По координатам города отправляется запрос погоды. Репозиторий создаёт `Weather` и `ForecastDay`.
8. После `await` проверяется `mounted`, затем результат записывается через `setState` и появляется на экране.

`Future` означает результат, который появится позже. `async` позволяет использовать `await`.
Во время ожидания интерфейс продолжает работать. `mounted` защищает от обновления уже закрытого экрана.
`setState` сам ничего не скачивает и не сохраняет: он сообщает Flutter, что интерфейс надо перестроить.

Сетевой запрос не вызывается из `build`. Иначе повторная отрисовка могла бы каждый раз отправлять новый запрос.
Поиск запускается нажатием кнопки или Enter; запрос не отправляется на каждую введённую букву.

## Где находятся адреса и параметры

В `WeatherApiClient`:

- `searchCities` — `geocoding-api.open-meteo.com/v1/search`, параметры `name`, `count=5`, `language=ru`.
- `getWeather` — `api.open-meteo.com/v1/forecast`, координаты, показатели `current`, список `daily`, `forecast_days=5`.

`Uri.https` сам кодирует русский текст, пробелы и другие символы запроса.
API-клиент не знает, какие карточки рисует экран. Экран не собирает сетевые адреса.
Сервис для учебного некоммерческого доступа не требует ключа; секретов в проекте нет.

Единицы задаются явно: `temperature_unit=celsius`, `wind_speed_unit=ms`. Давление API возвращает в гПа.
`timezone=auto` выбирает пояс по координатам города. Показываются компоненты времени, которые прислал сервис,
без дополнительного преобразования в пояс устройства.
`DateTime.parse` строки без смещения не сохраняет название пояса города: здесь дата используется для показа её компонентов,
а не для расчётов между часовыми поясами. Полноценное управление часовыми поясами в работу не добавлено.

## Как читается прогноз

В ответе `current` содержит одиночные значения, а `daily` — несколько параллельных списков.
Например, `daily['time'][0]`, `daily['temperature_2m_min'][0]` и `daily['weather_code'][0]`
описывают один и тот же первый день.
Обычный цикл `for` проходит по индексам и создаёт `ForecastDay`.
Если ответ содержит меньше трёх дней или обязательные данные неверного типа, показывается ошибка разбора.

`weather_code` — число, а не готовое описание. В `weatherDescriptions` оно связывается с русским текстом.
Например, 73 — снег. `weatherIcon` выбирает встроенный значок через обычные `if`.
Для неизвестного кода есть запасные текст и значок.
`formatTemperature` округляет значение и добавляет плюс только для положительной температуры.

## Какие состояния есть у экрана

| Поле | Назначение |
| --- | --- |
| `isLoading` | Идёт запрос, показывается индикатор и блокируются новые запросы |
| `weather` | Успешный результат либо `null` |
| `error` | Сообщение сетевой ошибки либо `null` |
| `hasSearched` | Позволяет отличить начальную подсказку от пустого результата поиска |
| `cities` | Найденные города для выбора |
| `selectedCity` | Город, по которому надо загрузить или повторить погоду |
| `lastQuery` | Последний отправленный запрос поиска для повтора |
| `inputError` | Ошибка пустого ввода под полем |
| `favoritesReady` | Успешно ли загружено избранное |
| `savingFavorite` | Идёт ли запись избранного |
| `favoritesError` | Ошибка чтения избранного, отдельно от ошибок погоды |

Состояние успеха определяется наличием `weather`. Пустой результат — поиск завершён без ошибки,
но список городов пуст. Отдельный enum или сложная система состояний здесь не нужны.
`late final repository` получает значение один раз в `initState`, когда уже можно обратиться к `widget.repository`.
Тип с `?` допускает `null`; `!` используется только там, где наличие значения уже проверено.
Для временно недоступной кнопки `onPressed` равен `null` — Flutter сам показывает её выключенной.

`retry()` повторяет запрос погоды для `selectedCity`. Если ошибка была ещё при поиске,
повторяет сохранённый `lastQuery`, даже если пользователь уже изменил текст в поле.

## Как обработаны ошибки

`WeatherException` — простой класс с текстом ошибки. Он передаёт понятную причину от клиента к экрану.
`throw` прерывает обычное выполнение и передаёт ошибку обработчику `catch`.

| Ситуация | Что происходит |
| --- | --- |
| HTTP 200 | JSON разбирается дальше |
| HTTP 404 | Сообщение о ненайденном адресе сервиса |
| HTTP 500 и другие 5xx | Сообщение об ошибке погодного сервиса |
| HTTP 429 | Предложение подождать перед повтором |
| Другой HTTP-код | Сообщение с кодом ответа |
| Нет связи, ошибка соединения | Перехватывается `http.ClientException`, предлагается проверить интернет |
| Ответ не пришёл за 15 секунд | Перехватывается `TimeoutException`, можно повторить |
| Неверный JSON или обязательные поля | Сообщение о некорректных данных |
| Неизвестный город | Успешный ответ с пустым списком; это отдельный результат, а не HTTP 404 |

`utf8.decode(response.bodyBytes)` правильно читает русские символы из байтов ответа.
Проверка статуса идёт до разбора JSON: при ошибке сервер может прислать обычный текст или HTML.
Кнопка «Повторить» появляется при ошибке. «Город не найден» предлагает исправить название.

## Как сохраняется избранное

`FavoritesRepository` использует `shared_preferences`, как предыдущие лабораторные.
Список городов превращается в список карт, затем в JSON-строку и сохраняется под ключом `weather_favorites`.
В браузере это LocalStorage. При запуске `loadFavorites()` вызывается из `initState`.

`toggle` добавляет отсутствующий город или удаляет уже добавленный по ID.
Сначала создаётся копия списка, затем сохраняется новое содержимое. Только после успешной записи
заменяется видимый список. Если запись не удалась, звезда не показывает ложное успешное сохранение.
`removeWhere` удаляет элементы, для которых переданная функция возвращает `true`.

При ошибке чтения избранного его изменение заблокировано до успешного повтора,
чтобы не затереть непрочитанные данные. Сама погода продолжает работать.
При ошибке записи появляется сообщение, действие можно выполнить снова.

После обновления страницы избранные города восстанавливаются, но погоду надо получить из сети заново.
Сохранение городов не является кэшем погодных данных.
Используй тот же браузер, хост и порт: `127.0.0.1:8755` и `localhost:8755` — разные адреса хранения.

## Как устроен интерфейс

`WeatherApp` — `StatelessWidget`, потому что только задаёт тему и первый экран.
`WeatherScreen` — `StatefulWidget`, потому что поисковый результат меняется.
`WeatherState` — его обычный объект `State`, а не отдельный пакет.

`ListView` позволяет прокручивать весь экран, `ConstrainedBox(maxWidth: 720)` ограничивает ширину на компьютере.
`Expanded` отдаёт полю ввода место рядом с кнопкой. `Wrap` переносит показатели погоды, если они не помещаются в строку.
`buildCurrentWeather`, `buildForecastDay` и `buildCityCard` — обычные функции, возвращающие виджеты.
`return Card(...)` описывает карточку, а нажатие позже запускает `onTap` или `onPressed`.

`TextEditingController` читает текст. `ScrollController` возвращает прокрутку к началу при выборе города.
Оба освобождаются в `dispose`, там же закрывается HTTP-клиент.
`ValueKey` связывает карточку с ID города и её назначением: результат поиска или избранное.
`context` используется в стандартных методах Flutter и для `SnackBar`, дополнительной архитектуры через контекст нет.

## Контрольные вопросы из ТЗ

**Какие состояния должен иметь сетевой экран?** Загрузка, успех, ошибка. Для поиска ещё нужен пустой результат,
а перед первым запросом полезна начальная подсказка. Они различаются полями состояния, перечисленными выше.

**Где размещать API client?** В отдельном слое данных, здесь `lib/data/weather_api_client.dart`.
Он хранит адреса и параметры, выполняет запрос, проверяет HTTP-код и возвращает JSON репозиторию.

**Как обработать HTTP 404 и 500?** Сначала проверить `statusCode`. 404 — адрес ресурса не найден,
500 — внутренняя ошибка сервиса. Показать понятный текст и возможность повтора, не пытаться принять ошибку за успешную погоду.

**Зачем нужен repository?** Экрану нужны города и погода, а не детали JSON.
Репозиторий вызывает клиент и создаёт модели. Поэтому изменение формата API не требует переписывать весь интерфейс.

## Небольшие правки для тренировки

| Просьба преподавателя | Где изменить |
| --- | --- |
| Прогноз на три дня вместо пяти | `WeatherApiClient.getWeather`, `forecast_days` |
| Больше найденных городов | `WeatherApiClient.searchCities`, `count` |
| Другой тайм-аут | `WeatherApiClient.getJson`, `Duration(seconds: 15)` |
| Переименовать описание снега | `weather_display.dart`, карта `weatherDescriptions` |
| Другой значок дождя | `weather_display.dart`, функция `weatherIcon` |
| Сделать шрифт температуры меньше | `buildCurrentWeather`, `fontSize: 48` |
| Светлая тема | `main.dart`, сменить `Brightness` и тёмные значения фона |
| Не загружать единственный город автоматически | `WeatherState.searchCities`, блок `results.length == 1` |
| Показать только название города в главной карточке | `buildCurrentWeather`, `fullName` заменить на `name` |
| Спрятать давление | `buildCurrentWeather`, условный `Text` с давлением |

## Что проверено

20.10.2026: `flutter analyze` без замечаний, `flutter test` — 31 тест успешно,
`flutter build web` — успешная сборка.
Тесты покрывают шесть сценариев из ТЗ, обработку HTTP-кодов, неверные данные,
повтор запроса, несколько городов, избранное, его восстановление и ошибки хранения.
Проверены экран 320×568, масштаб текста 1,5, клавиатура и длинные названия.
Отдельно просмотрены отрисованные Flutter-экраны 390×844 и 1200×800 с тестовыми погодными данными.

Настоящий репозиторий также выполнил запросы к сервису: получил город Ханты-Мансийск,
текущую погоду, пять дней прогноза и пустой результат для вымышленного названия.
Сетевые ошибки в тестах имитируются, реальный интернет устройства не отключался.
Ручной сценарий браузера и запуск Android не проверялись.

Для демонстрации: найти город, показать показатели и пять дней, добавить звезду, обновить страницу,
выбрать город из избранного, проверить пустой ввод и вымышленное название.
Для демонстрации отсутствия связи можно самостоятельно временно отключить сеть и нажать обновление,
затем включить сеть и нажать «Повторить».
